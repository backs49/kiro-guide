# 스펙 주도 개발 (Spec-driven)

<span class="level">L0</span> Kiro를 다른 AI 코딩 도구와 구분 짓는 핵심 개념입니다. 기능을 바로 코드로 만들기 전에 **무엇을 만들지 문서로 합의**하는 단계를 둡니다.

## 왜 스펙부터 쓰나

채팅 한 번으로 큰 기능을 맡기면 이런 문제가 생기기 쉽습니다.

- 요구사항을 에이전트가 임의로 해석해 엉뚱한 범위까지 고친다.
- 무엇이 끝났고 무엇이 남았는지 추적하기 어렵다.
- 리뷰어가 "왜 이렇게 만들었는지" 근거를 찾을 수 없다.

스펙 주도 개발은 이 문제를 **요구사항 → 설계 → 작업 목록**의 세 문서로 나눠 해결합니다. 각 단계에서 사람이 검토·수정한 뒤 다음 단계로 넘어갑니다.

## 세 단계 흐름

```text
요구사항 (requirements.md)   ← 사용자 스토리 + 인수 조건
        │  검토·승인
        ▼
설계 (design.md)              ← 구조, 컴포넌트, 데이터 모델, 흐름
        │  검토·승인
        ▼
작업 목록 (tasks.md)          ← 구현 단위로 쪼갠 체크리스트, 진행 상태 추적
        │
        ▼
작업 단위로 구현 → 테스트 → 리뷰
```

스펙 파일은 프로젝트의 `.kiro/specs/<기능 이름>/` 폴더에 저장되므로 **Git으로 버전 관리하고 PR에서 함께 리뷰**할 수 있습니다.

## 스펙의 종류

| 종류 | 언제 쓰나 | 첫 문서 |
|------|-----------|---------|
| **Feature Spec** | 새 기능 개발. Requirements-First 또는 Design-First 흐름 선택 | `requirements.md` |
| **Bugfix Spec** | 버그 진단·수정. 현재 동작 / 기대 동작 / **바뀌면 안 되는 동작**을 기록해 회귀를 막음 | `bugfix.md` |
| **Quick Spec** | 이미 잘 이해된 기능. 단계별 승인 없이 세 문서를 한 번에 생성 | — |

자세한 사용법은 [Specs](/features/specs), 실전 예시는 [기능 추가 스펙 레시피](/recipes/feature-spec)와 [버그 수정 스펙 레시피](/recipes/bugfix-spec)를 보세요.

## 언제 스펙을 쓰지 않아도 되나

공식 문서는 Feature Spec이 버그 수정이나 탐색용 코딩을 위한 것이 아니라고 설명합니다. 다음은 일반 채팅(Vibe)으로 처리해도 충분합니다.

- 한두 파일짜리 단순 수정, 오타·로그 메시지 변경
- "이 코드가 무슨 일을 하지?" 같은 질문과 탐색
- 일회성 스크립트 작성

::: tip 엔터프라이즈 개발자에게
요구사항 정의서 → 설계서 → WBS로 이어지는 익숙한 산출물 흐름을 **기능 단위로 작게** 돌린다고 생각하면 이해가 쉽습니다. 차이점은 각 문서를 에이전트가 초안으로 만들고, 사람이 검토·수정한다는 점입니다.
:::
